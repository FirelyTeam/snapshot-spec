## OQ-001 — Cardinality diamond (0..1 element typed with a profile whose root is 0..*)

**Verdict: discussed-unresolved.** Nobody on Zulip endorses ".NET's answer" (type-profile root wins, even when it *loosens* the element). Three positions exist and a tracker was filed (GF#19756, 2018) to document one of them; whether it landed as the R5 §5.4.6.1 root-cardinality rule should be checked in the JIRA sweep. Important side-finding: in 2018 Michel stated the intended *semantics* as "further constrain (but not relax)" while also stating that the .NET generator simply overrides with the inherited values and does not verify them, leaving verification to a validator check. So the loosening at `ElementDefnMerger.cs:689-695` is a **known 2018 gap between stated semantics and implementation** (verification delegated to a validator step that never existed), not a later regression.

   https://chat.fhir.org/#narrow/channel/179166-implementers/topic/cardinality.20of.20root.20elements/near/154024442

But it can be constrained") and extends it to datatype profiles (a 0..1 MRN Identifier profile *would* bound a referencing element). **Michel (id 154024475):** .NET follows Lloyd's interpretation — the referencing profile may "further constrain (but not relax)" — but the generator overrides with the inherited values and "does no attempt to verify the actual values", leaving that to the validator.
   Relevance: this is the exact diamond. Lloyd's reading makes the answer "element keeps 0..1 (a legal constraint of the 0..* root)"; Chris's makes it "root cardinality never merges"; both agree the profile root must never *loosen* the element — i.e. Zulip consensus against the current .NET output, and Michel's 2018 description already shows the override-without-verification gap that produces it.

## OQ-021 / DEV-025 — How much must a snapshot materialize?

**Verdict: discussed-unresolved** overall, with one sub-question effectively **answered informally** (depth rule) and one sub-question **dated and explained** (Java's slicer-children copy-down = FHIR-50391, mid-2025). Sub-findings:

- **(a) Depth / element set:** Lloyd 2021 — "depth equals that in the differential" (+ backbone exception); Grahame 2016 — "either you reference a type, or you inline the type" (all or nothing); Lloyd 2021 — inline downward until the child can be validated from the type profile alone. Consumer side: Ewout 2017 (#conformance "Walking into a contained resource", near/153896010) — the .NET validator assumes that if a snapshot element has children, it has *all* its children; and Ewout 2017-06-30 (#conformance "Need help with invariant on extensions", near/153895823) — a diff constraint on a datatype child causes the node to be expanded with all its siblings copied. Informal consensus, never spec text; this is why OQ-021 bites .NET validation specifically.
- **(b) Slicer → slice copy-down:** the April 2025 thread concluded slicer *properties* (binding, MS, …) are **not** propagated into slices' snapshots (Lloyd's wording: "not necessary for validation"), and Grahame *proposed* a spec note saying the slicer's constraints apply regardless (Rob, Eric and Lloyd reworded it; landing in the spec is not confirmed on Zulip). Then "Recent Snapshot generation changes." (2025-06-27) shows Java **did** start materializing the slicer's *children* into every slice (`Organization.identifier:NPI.id` …) and Grahame confirmed it is the FHIR-50391 outcome. That is DEV-025 flavor 2, dated, on the very US Core Organization fixture (org2a). Net outcome per Zulip: slicer *properties* do not propagate (text proposed to say they apply anyway) + slicer *children* materialize into slices (June 2025) — a hybrid nobody stated as such; JIRA (FHIR-50391) to confirm. Grahame had said such propagation is possible "only at the first level" and creates retrospective-content problems. Boundary: constraints added to a *slicer* in a derived profile do **not** flow into slices inherited from the parent (Grahame 2026-08-04: "otherwise we'd have multiple inheritence"). Lloyd in 2025-12 and 2026-06 still says the tools "can't" do slicer→slice propagation — in tension with the June 2025 implementation; recorded, not resolved.
- **(c) Recursion / contentReference depth:** not found beyond Michel 2017 ("expanded on demand … infinitely deep").
- **(d) `type.profile` as validator instruction:** see OQ-002 thread 4 — Grahame/Lloyd 2025-11: the snapshot does not pull in referenced datatypes.
- **Min cardinality:** Lloyd 2026-01 — "minimum cardinality should *not* be inherited by slices"; Grahame fixed a Java closed-slicing bug (hapifhir/org.hl7.fhir.core#2282).

Caution for the register: DEV-025/OQ-021 currently describe the copy-down as "in tension with" `APPLY_PROPERTIES_FROM_SLICER=false`. Zulip suggests they are two halves of one FHIR-50391 outcome (entry *children* materialize into slices; entry *properties* do not). The JIRA text of FHIR-50391 was not read in this sweep — confirm there before rewording.

## General findings (cross-cutting)

- **Ewout's own thread, 2026-09-01 · #conformance · "Issue 13402 - Clarify snapshotting rules"** — https://chat.fhir.org/#narrow/channel/179177-conformance/topic/Issue.2013402.20-.20Clarify.20snapshotting.20rules/near/620626646 — Grahame: "sure we can look at that" (re filing Java bugs). **Gino Canessa** posted a fresh independent comparison: https://ginoc.io/202609-snapshot/snapshot-generation-comparison.html ("Concrete observable cases" section) — a new external artifact for the WGM brief.
- **"Snapshot generation is tooling / rules live in tests":** Lloyd 2026-01-27 (#conformance "How to differentiate extensions in StructureDefinitions?", near/570433270): the shared tests "define the rules for snapshot generation and validation"; putting formal rules in the spec was considered but "they get super ugly". Grahame 2026-01-28: the id syntax is a written rule, but he does not know whether "other snapshot generators (there's at least 2 others)" follow it. Grahame 2025-12-09: reference tests are `fhir-test-cases/r5/snapshot-generation` and `rX/snapshot-generation`.
- **Inlining types is optional, per Grahame (2016-10):** his Baltimore recap — types must inherit correctly; inlining them into the snapshot is optional; without inlining, consumers must resolve the types (#conformance "Snapshot Generation", near/153854064); "I object strenuously to making it always required". Michel's counter: a partial snapshot is "incomplete and unreliable". This is the root of OQ-002/OQ-021(d).
- **Descriptive-property override rationale (Java):** Lloyd 2024-11-29 — type override exists for extensions; Grahame 2024-11-30 — "wasn't intended to work for types"; Lloyd 2025-05 — "A type has no meaning of its own". Firely (Simplifier/.NET) does the opposite and customers (Nictiz, PS-CA) depend on it (Ward 2026-02).
- **.NET vs Java are close in practice:** Grahame 2025-02-12 (#dotnet "Snapshot generation", near/499283993): "our snapshots are remarkably close - much closer than I expected"; differences noted: isCommonBinding extensions, markdown link absolutization, `Resource.id` type workaround, discriminator path `value`→`valueCode` rewriting (Ewout 2025-05-06 surprised .NET does that).
- **Test-case merging agreed in principle:** Grahame/Ewout 2025-05-06 (#tooling "New Snapshot functionality", near/516384650): "we should also discuss if we can merge test cases - I have 100s of them now"; Ewout: needs them to avoid regressions. Same thread: Grahame's `structuredefinition-additionalBase` proposal (multiple inheritance for constraint profiles; additional-base differentials merged into the differential pre-snapshot; slicing must be identical) — Ewout's algorithm sketch (apply C's diff to A's snapshot, then B's diff) accepted as equivalent "as long as it's the same outcome".
- **Obligations at root → propagate in snapshot?** Lloyd 2024-11-20 (#fhir/infrastructure-wg "Obligations", near/483494571): it is "reasonable to propagate from the root to the individual elements" during snapshot generation; the snapshot would show where the rules apply. A further materialization dimension not in the register.
- **2017 alignment intent:** Ewout 2017-03-28 (#conformance "Test Cases for Snapshot Generation", near/153880049): wants the .NET and Java generators "closely aligned" so a build-wide differential/snapshot comparison becomes possible. Michel: .NET completes the differential with missing parents first; Lloyd/Grahame: sliced parents must be present in the diff.
- **Extension-slice cardinality bugs in Java (2025-05):** see OQ-001 thread 3 — the "extension root as template" rule is intended; Grahame fixes edge cases as reported.
- **2023 ecosystem survey:** Grahame found hundreds of published profiles applying datatype profiles to elements (au-paididentifier, ch-core-gln-identifier, IHE.MHD.UniqueIdIdentifier, dk-core-cpr-identifier, hpi-nz-address, ch-emed-range …) — the population any change to type-profile merging would affect ("Broken snapshot generation", near/360411653).

## 0. Entry point and unconditional invocation

`ProfileUtilities.generateSnapshot` runs the preprocessor unconditionally on a **clone** of every differential, immediately before the main base-vs-diff walk (ProfileUtilities.java:824-825):

```java
StructureDefinitionDifferentialComponent diff = cloneDiff(derived.getDifferential()); // we make a copy here because we're sometimes going to hack the differential while processing it. Have to migrate user data back afterwards
new SnapshotGenerationPreProcessor(this).process(diff, derived);
```

`process` (L134-153) calls `processSlices(diff, srcWrapper)` at L136 unconditionally; the rest of `process` (L137-152) is the additional-base machinery, gated on `EXT_ADDITIONAL_BASE` and out of scope here.

The class javadoc (L41-50) **claims**: "when a slice is encountered, it may have additional details defined after the slice that must be merged into each of the slices … This class pre-processes the differential, finding the slices that have these trailing properties, and filling them out in the slices that follow" and admits "There's potential problems here, mostly around slicing extensions (other kind of slicing isn't allowed) and also the merging logic might need to be sophisticated." As shown in §4, the merging logic is in fact naive (path+sliceName matching) and produces cross-slice contamination.

## 1. `processSlices` (L688-741) — the driver

### 1.1 The `SliceInfo` inner class (L86-121) and its routing rules

```java
public class SliceInfo {
    SliceInfo parent;
    String path;
    boolean closed;
    ElementDefinition slicer;
    List<ElementDefinition> sliceStuff;
    List<ElementDefinition> slices;
```

- **Constructor** (L94-102): stores `path = ed.getPath()`, `slicer = ed`, creates an empty `sliceStuff` list, leaves `slices` **null**, and — crucially — forwards the slicer element itself into the parent's content: `if (parent != null) { parent.add(ed); }` (L99-101). So a nested slicing entry becomes part of its parent's sliceStuff (if the parent has not yet seen named slices), which is exactly what the bail-out at L713-723 later detects.
- **`newSlice`** (L104-112): lazily creates `slices` on first named slice, adds to it, and forwards to parent (`parent.add(ed)`).
- **`add`** (L113-120), quoted in full:

```java
public void add(ElementDefinition ed) {
  if (slices == null) {
    sliceStuff.add(ed);
  }      
  if (parent != null) {
    parent.add(ed);
  }
}
```

  Routing rule: an element goes into `sliceStuff` **only while `slices == null`**, i.e. only content appearing after the slicing entry but **before the first named slice**. Once `newSlice` has run, later `add`ed elements (the children of named slices) are silently dropped for this SliceInfo — there is no `else`; they are recorded nowhere in it (slice ranges are recomputed later from the raw element list by `findEndOfSlice`). The forward to `parent` is **always** executed, so an element inside an inner slicing's region also lands in every enclosing SliceInfo's sliceStuff (again, only while that ancestor's `slices == null`).

### 1.2 First pass: partitioning (L689-711)

```java
for (int cursor = 0; cursor < diff.getElement().size(); cursor++) {      
  ElementDefinition ed = diff.getElement().get(cursor);

  SliceInfo si = getSlicing(ed);
  if (si == null) {
    if (ed.hasSlicing() && !isExtensionSlicing(ed)) {
      si = new SliceInfo(null, ed);
      slicings.add(si);
    } else {
      // ignore this
    }
  } else {
    if (ed.hasSliceName() && ed.getPath().equals(si.path)) {
      si.newSlice(ed);
    } else if (ed.hasSlicing() && !isExtensionSlicing(ed)) {
      si = new SliceInfo(si, ed);
      slicings.add(si);
    } else {
      si.add(ed);
    }
  }
}       
```

Decision order for an element inside an open SliceInfo (L702-709):
1. `hasSliceName() && path == si.path` → **named slice** (`newSlice`). Note this check comes FIRST: a named slice element that itself carries a `slicing` component (a reslicing setup) is registered only as a slice — no SliceInfo is created for its reslicing, and its reslices (same path, sliceName like `"group/x"`) are registered as further ordinary slices of the same outer SliceInfo.
2. Otherwise `hasSlicing() && !isExtensionSlicing(ed)` → **nested SliceInfo** (parented; the constructor also adds the slicer element to the parent's sliceStuff if still open).
3. Otherwise → `si.add(ed)` (sliceStuff if pre-first-slice, else dropped locally / forwarded to ancestors).

Elements at paths not under any open SliceInfo, and top-level extension slicings, are ignored (L698-699 `// ignore this`).

### 1.3 `getSlicing` (L1088-1100) — which SliceInfo an element belongs to

```java
private SliceInfo getSlicing(ElementDefinition ed) {
    for (int i = slicings.size() - 1; i >= 0; i--) {
      SliceInfo si = slicings.get(i);
      if (!si.closed) {
        if (si.path.length() > ed.getPath().length()) {
          si.closed = true;
        } else if (ed.getPath().startsWith(si.path)) {
          return si;
        }
      }
    }
    return null;
}
```

- Iterates newest-first, so the innermost matching SliceInfo wins.
- A SliceInfo is closed as a side effect the first time a *shorter-path* element is looked up (pure `length()` comparison, L1092), after which it can never absorb content again. An element with an equal-length non-matching path does not close it but falls through to older SliceInfos.
- The membership check is raw `String.startsWith` with **no segment-boundary guard** (L1094): a slicing on `A.id` would claim a later element at `A.identifier...`. Latent hazard; not exercised by the test case examined. Note it also relies on differential element ordering — an element can only be claimed while the SliceInfo is still open.

### 1.4 `isExtensionSlicing` (L1077-1086) — the exemption, quoted in full

```java
private boolean isExtensionSlicing(ElementDefinition ed) {
    if (!Utilities.existsInList(ed.getName(), "extension", "modiferExtension")) {
      return false;
    }
    if (ed.getSlicing().getRules() != SlicingRules.OPEN || (!ed.getSlicing().hasOrdered() || ed.getSlicing().getOrdered()) || ed.getSlicing().getDiscriminator().size() != 1) {
      return false;
    }
    ElementDefinitionSlicingDiscriminatorComponent d = ed.getSlicing().getDiscriminatorFirstRep();
    return d.getType() == DiscriminatorType.VALUE && "url".equals(d.getPath());
}
```

Verified supporting facts:
- `ElementDefinition.getName()` returns the **last path segment** (ElementDefinition.java:13101-13103 at this commit: `return hasPath() ? getPath().contains(".") ? getPath().substring(getPath().lastIndexOf(".")+1) : getPath() : null;`).
- **The `"modiferExtension"` typo (L1078)**: since `"modifierExtension"` never equals the misspelled `"modiferExtension"`, a slicing on a `modifierExtension` element can NEVER qualify as extension slicing. The exemption list is de facto `{extension}` only.
- **The ordered clause (L1081)**: `(!ed.getSlicing().hasOrdered() || ed.getSlicing().getOrdered())` makes the guard *fail* (→ not extension slicing) when `ordered` is **absent** or **true**. To be exempted, a slicing must state `ordered=false` **explicitly**, plus `rules=open`, plus exactly one discriminator, of type `value` with path `url`.

**Consequence** (which slicings get propagation vs are skipped): only slicings on an element literally named `extension` with `rules=open`, explicit `ordered=false`, and exactly the single discriminator `value:url` are exempt — they never form a SliceInfo, so their trailing content and slices belong to the enclosing SliceInfo's bookkeeping. Everything else — non-extension slicings, `modifierExtension` slicings (typo), extension slicings that omit `ordered` (very common in the wild), state `ordered=true`, use `rules=closed`/`openAtEnd`, or use a different/extra discriminator — creates a SliceInfo. That has two effects: (a) trailing-property propagation applies to its named slices; (b) if such a slicing entry occurs *inside another SliceInfo's sliceStuff*, it triggers the total bail-out below. In `on-questionnaire-input.xml` every extension slicing writes `<ordered value="false"/>` (e.g. lines 95-102, 326-334), so all are exempt and no bail-out fires.

Message text verbatim (Messages.properties:1155):

**Confirmed: the `return` exits `processSlices` entirely.** It sits before both the merge loop (L726-736) and the `markExtensions` pass (L738-740), so ONE non-extension slicing found inside ONE slicing's trailing region abandons trailing-property propagation for EVERY slicing in the differential, and also skips the final `ProfileUtilities.markExtensions` pass. It is a log-warn, not an error — snapshot generation proceeds without the preprocessing. The trigger condition is narrow, though: the offending SliceInfo must have both non-empty `sliceStuff` and `slices != null` (i.e. propagation would actually have happened for it); a nested slicing inside a slicing that never receives named slices does not trigger the bail-out.

### 1.6 Merge loop — backwards iteration (L725-736)

```java

      SliceInfo si = slicings.get(i);

```

Mechanical fact: `slicings` is in creation (document) order, so reverse iteration processes the **most recently created — i.e. innermost/latest — slicings first**. Propagation happens only when the SliceInfo has both trailing content and at least one named slice (L728). *Analysis (not stated in code):* since `mergeElements` mutates the shared `diff.getElement()` list by injecting copies, innermost-first ordering lets each inner slicing's ranges be completed before an enclosing slicing scans across them; outer-first would let an outer merge inject elements into inner ranges that the inner merge then re-matches.

## 2. `mergeElements(List<ED> elements, List<ED> allSlices, ED slice, ED slicer)` (L743-810) — per-slice merge

Called once per named slice, with `elements` = the whole differential list, `allSlices` = the SliceInfo's sliceStuff, `slice` = the named-slice anchor element, `slicer` = the slicing entry.

### 2.1 Slice range

```java
int sliceIndex = elements.indexOf(slice);
int startOfSlice = sliceIndex + 1;
int endOfSlice = findEndOfSlice(elements, slice);
```

`findEndOfSlice` (L982-991), quoted in full:

```java
private int findEndOfSlice(List<ElementDefinition> elements, ElementDefinition slice) {
    for (int i = elements.indexOf(slice); i < elements.size(); i++) {
      ElementDefinition e = elements.get(i);
      if (!(e.getPath().startsWith(slice.getPath()+".") ||
          (e.getPath().equals(slice.getPath()) && slice.getSliceName().equals(e.getSliceName())))) {
        return i-1;
      }
    }
    return elements.size() - 1;
}
```

The range extends over consecutive elements that are either (a) path-descendants of the slice path (note: descendants of *any* depth, including the contents of inner extension slices — this is the M1q surface), or (b) at the same path with the **same** sliceName. Consequences:
- A reslice (`sliceName = "group/x"`, same path) terminates the range — `"group/x" ≠ "group"` — and, having been registered by `newSlice` (§1.2), gets its own `mergeElements` call as an ordinary slice.
- A (schema-illegal) consecutive duplicate with same path AND same sliceName would extend the range.
- The path check is again `startsWith(path+".")` on strings, so no cross-sibling leakage is possible here (the dot guard is present, unlike `getSlicing`).

### 2.2 Match census and the two branches (L753-808)

First a census: for each sliceStuff element, is there at least one match in the range?


(The `missing` set is populated at L765 but **never read afterwards** — dead code.)

**Branch A — `allFound` (L770-778):** every pair `(j, i)` in range × sliceStuff is tested and every match merged:


**Branch B — not all found (L779-808):** same all-pairs merge, additionally recording which sliceStuff elements matched anything (`handled`), then **injecting** the unhandled ones:

```java

    ElementDefinition edc = ed.copy();
    edc.setUserData(UserDataNames.SNAPSHOT_PREPROCESS_INJECTED, true);

```

Key facts:
- **Id rewrite, verbatim (L799):** `String id = ed.getId().replace(slicer.getId(), slice.getId());` — a plain `String.replace` of *every* occurrence of the slicer's id substring by the slice's id (e.g. `Questionnaire.item.extension:hidden.value[x]` → `Questionnaire.item:display.extension:hidden.value[x]` when slicer id is `Questionnaire.item` and slice id is `Questionnaire.item:display`). No segment-boundary guard, but since the slicer id is a strict prefix of every sliceStuff id, in practice only the prefix occurrence exists.
- Injection copies the whole element (`ed.copy()`, L801) — so injected elements keep ALL their properties, including ones `merge()` never propagates (e.g. `mapping`). Matched elements, in contrast, receive only the `merge()` property set (§3). This match-vs-inject asymmetry is observable in the on-questionnaire expected output (§4.4).
- Marker (L802): `edc.setUserData(UserDataNames.SNAPSHOT_PREPROCESS_INJECTED, true);` — `UserDataNames.SNAPSHOT_PREPROCESS_INJECTED = "SNAPSHOT_PREPROCESS_INJECTED"` (UserDataNames.java:141). Within the r5 module at this commit the marker is **write-only** (git grep over `org.hl7.fhir.r5` finds only the setter); consumers elsewhere were not verified (sparse clone, search constraints).
- `endOfSlice++` keeps the range consistent as injections happen; `elements.indexOf` lookups are on the live, mutated list.
- Match cardinality is **many-to-many**: one range element can be merged from several sliceStuff elements (j-outer/i-inner loop, no break), and one sliceStuff element can merge into several range elements (it is `handled` after the first, but still merges into all matches). For any single property, the first sliceStuff element (document order) that possesses it wins, since after the first fill the focus `has` the property.

## 3. `merge(ED focus, ED base)` (L993-1075) — THE PROPERTY TABLE

`focus` = the element inside the slice range; `base` = the sliceStuff element. **Every property uses the identical fill-if-absent guard** `if (base.hasX() && !focus.hasX())` — there is no unconditional overwrite, no append-to-existing, and no value reconciliation of any kind. List-valued properties are `addAll`ed, but only when the focus list is completely empty — so effectively also fill-if-absent, NOT union/append semantics.

**No `.copy()` is used anywhere in `merge()`.** Scalar setters install the base's element object, and `addAll` inserts the base's list items, by reference. Since the same sliceStuff element is merged into every named slice, the resulting elements of different slices share the same `Binding`/`TypeRefComponent`/`Constraint`/`StringType` object instances (aliasing). Contrast: the injection path uses `ed.copy()` (L801).

## 4. `elementsMatch` + `pathsMatch` and the M1q cross-slice contamination analysis

### 4.1 Both methods, quoted completely

`elementsMatch` (L812-822):

```java
private boolean elementsMatch(ElementDefinition ed1, ElementDefinition ed2) {
    if (!pathsMatch(ed1.getPath(), ed2.getPath())) {
      return false;
    } else if (ed1.getSliceName() != null && ed2.getSliceName() != null) {
      return ed1.getSliceName().equals(ed2.getSliceName());
    } else  if (ed1.getSliceName() != null || ed2.getSliceName() != null) {
      return false;
    } else {
      return true;
    }
}
```

(`getSliceName()` returns Java `null` when the element has no sliceName — ElementDefinition.java:6487-6489.)

`pathsMatch` (L824-845):

```java
private boolean pathsMatch(String path1, String path2) {
    if (path1.equals(path2)) {
      return true;
    }
    if (path1.endsWith("[x]")) {
      path1 = path1.substring(0, path1.length()-3);
      if (path2.startsWith(path1)) {
        if (!path2.substring(path1.length()).contains(".")) {
          return true;
        }
      }
    }
    if (path2.endsWith("[x]")) {
      path2 = path2.substring(0, path2.length()-3);
      if (path1.startsWith(path2)) {
        if (!path1.substring(path2.length()).contains(".")) {
          return true;
        }
      }
    }
    return false;
}
```

`[x]` tolerance: `foo.value[x]` matches `foo.value[x]`, `foo.valueString`, `foo.valueCodeableConcept` — any same-stem leaf without a further `.` — in either direction. (It would also match a hypothetical sibling literally named `valueSomething`; FHIR naming rules make that a theoretical rather than practical hazard.)

### 4.2 The mechanism — what the match key actually is

The match key is exactly the pair **(path modulo `[x]`, sliceName-or-null)**. Nothing else: not the element id, not the ancestry, not which extension slice a child belongs to. Two consequences:

1. **Descendant depth is flattened.** A slice's range (§2.1) spans ALL its path-descendants, including the children of *inner* (exempted) extension slices. Any two descendants at the same path are indistinguishable to `elementsMatch` unless their sliceNames differ.
2. **Extension-slice children are the canonical collision.** Every extension slice's `value[x]` child has path `<parent>.extension.value[x]` and NO sliceName — the identity that distinguishes them (`extension:enableWhenExpression.value[x]` vs `extension:itemControl.value[x]`) lives only in the **id**, which `elementsMatch` never consults. So a sliceStuff element that is the `value[x]` child of extension slice E1 matches the `value[x]` child of any OTHER extension slice E2 inside the target slice's range.

Under which conditions does a sliceStuff element match the "wrong" element:
- sliceStuff element with **no sliceName** at path P → matches EVERY no-sliceName element at path P (mod `[x]`) anywhere in the slice's descendant range, regardless of which inner slice parent it sits under. This is the M1q case.
- sliceStuff element **with** sliceName S at path P → matches any element at path P with sliceName S in the range. Same-named slices of *different* inner slicings at the same path would also collide (e.g. two different backbone children both sliced with a slice named "primary" — possible only at identical paths, i.e. for reslices or for extension slices that happen to share a name at the same path). The no-sliceName case is by far the commonly triggered one.
- The `[x]` tolerance widens this: sliceStuff `...value[x]` (no sliceName) also matches `...valueString` etc. in the range.

### 4.3 Minimal trigger shape (on paper)

```
Resource.x                       slicing (non-extension, any discriminator)   ← slicer; SliceInfo created
Resource.x.extension             slicing open/ordered=false/value:url        ← exempt; goes to sliceStuff
Resource.x.extension  sliceName=E1                                           ← sliceStuff
Resource.x.extension.value[x]    (no sliceName)  mustSupport=true            ← sliceStuff; INTENDED as E1's child
Resource.x  sliceName=S1                                                     ← first named slice; range starts
Resource.x.extension  sliceName=E2   (a different extension)                 ← inside S1's range
Resource.x.extension.value[x]    (no sliceName)  e.g. only a binding         ← INTENDED as E2's child
```

Result of `mergeElements(elements, sliceStuff, S1, slicer)`: the sliceStuff `value[x]` (child of E1) matches S1's `value[x]` (child of E2) — same path, both sliceName-null — and `merge()` fills `mustSupport=true` (and any other absent property in the §3 table: min, max, type, fixed, binding, …) into **E2's** child. Contaminated property in the minimal shape: `mustSupport`.

**Dual effect — the contamination has a shadow:** because the sliceStuff `value[x]` matched *something*, it is marked `handled` (L786) and is NOT injected. If S1 also declared E1 (without repeating the `value[x]` child), the intended propagation of E1's `value[x]` constraint into S1 silently does not happen. So the bug both adds the property where it doesn't belong and drops it where it does.

**Verdict: CONFIRMED.** The code can, under the stated conditions (outer non-exempt slicing with trailing content; trailing content contains a sliceName-less descendant at path P belonging to inner slice E1; the target named slice contains a sliceName-less descendant at the same P under a different inner slice E2), merge sliceStuff content into a child element belonging to a different inner slice than the author intended.

### 4.4 Empirical confirmation in `on-questionnaire` (fhir-test-cases @ 9f495e8, expected file generated by an unpinned validator version — commit-pair caveat)

The input (`on-questionnaire-input.xml`) has exactly the trigger shape at `Questionnaire.item`:

The discriminating evidence is the **mapping asymmetry** — merged elements got `mustSupport` but not `mapping` (which `merge()` lacks, §3), while injected elements kept both:

1. **Contamination (merge path).** `item:group.extension:itemControl.value[x]` — input (L559-565) has ONLY a binding; expected snapshot (expected L6854-6888) has `<mustSupport value="true"/>` and NO ontario mapping. Same for `item:question.extension:itemControl.value[x]` — input (L1049-1060) has binding + one ontario mapping, no mustSupport; expected snapshot (L16963+) has `mustSupport=true`, its own mapping, and NOT the renderStyle/hidden "hints/hint" mappings. The mustSupport plausibly cannot come from the base (the core `questionnaire-itemControl` extension SD setting mustSupport on its `value[x]` — inference, that SD was not read) and is exactly what the first matching sliceStuff element (`enableWhenExpression.value[x]`, mustSupport=true) fills in.
2. **Lost injection (spurious `handled`).** In the `group` and `question` ranges, the sliceStuff `value[x]` elements all matched foreign `value[x]` elements (itemControl, variable, choiceOrientation, …), so none were injected: the expected snapshot contains **no** `item:group.extension:renderStyle.value[x]`, `item:group.extension:enableWhenExpression.value[x]`, or `item:group.extension:hidden.value[x]` (grep over expected: zero hits) — the constraints the author wrote for those extensions' values never reach the group slice's own copies of those extensions.
3. **Correct-ish injection as the control.** The `display` slice's range contains NO element at path `Questionnaire.item.extension.value[x]` (display's extension slices at L831-863 have no `value[x]` children), so nothing matched → all three sliceStuff `value[x]` elements were **injected** (branch B): the expected snapshot has `item:display.extension:enableWhenExpression.value[x]` (L12992), `item:display.extension:hidden.value[x]` (L13160), and `item:display.extension:renderStyle.value[x]` (L13326) — the latter with BOTH `mustSupport=true` AND the ontario mapping `hints/hint[.='GREY_BG', 'WHITE_BG', 'BORDER']` (full-copy injection), and with the string-replaced ids (`Questionnaire.item` → `Questionnaire.item:display`).

### 4.5 `findEndOfSlice` edge cases (recap)

- Same path + same sliceName immediately following: extends the range (second disjunct L986) — only reachable with duplicate slice entries.
- Reslices (same path, sliceName `"a/b"`): terminate the parent slice's range, are separately registered as slices (§1.2), and get their own merge pass. `elementsMatch` compares full sliceName strings, so a sliceStuff element with sliceName `a` does not match a reslice child named `a/b`.

## 5. The insertion machinery (branch B injections)

### 5.1 `determineInsertionPoint` (L847-869)

Works backwards through the **rewritten id**, longest prefix first:

```java
String[] p = id.split("\\.");
for (int i = p.length-1; i >= 1; i--) {
  String subId = p[0]; 
  for (int j = 1; j <= i; j++) { subId += "."+p[j]; }
  List<ElementDefinition> peers = findPeers(elements, startOfSlice, endOfSlice, subId);
  if (!peers.isEmpty()) {
    for (ElementDefinition ed : peers) {
      if (comesAfterThis(id, path, edDef, ed)) {
        return elements.indexOf(ed);
      }
    }
    return elements.indexOf(peers.get(peers.size() -1))+1;
  }
}
return endOfSlice+1;
```

I.e.: find the longest dotted id-prefix that has any elements in the slice range (`findPeers`); insert before the first peer that should come after the new element, otherwise after the last peer. If no prefix at any length has peers, append after the end of the slice (`endOfSlice+1`).

### 5.2 `findPeers` (L871-880)

Range-restricted raw prefix scan: `if (ed.getId().startsWith(subId)) peers.add(ed);` — again no segment-boundary guard, but here matching descendants-and-self of the prefix is the intent.

### 5.3 `comesAfterThis` (L891-916)

Splits both ids on `.`; walks to the first differing segment `i`; orders by the two segment names' child indexes in the definition of the *parent* segment: `ElementAnalysis sed = edDef.get(i-1); int i1 = indexOfName(sed, p1[i]); int i2 = indexOfName(sed, p2[i]); ... return i1 < i2;` (L900-910). If one id is a prefix of the other, shorter comes first: `return p1.length < p2.length;` (L915).

**Slice-setup-after-slice special case (L903-909), verbatim:**

```java
        if (i == Integer.min(p1.length,  p2.length) -1 && i1 == i2) {
          if (!p1[i].contains(":") && p2[i].contains(":")) {
            // launched straight into slicing without setting it up, 
            // and now it's being set up 
            return true;
          }
        }
```

When the differing segment is the last comparable one, both segments resolve to the same definition child (`i1 == i2`), the new element's segment is unsliced (`foo`) and the existing peer's is sliced (`foo:bar`) — the new element (a slicing setup being injected for content that "launched straight into slicing") is placed BEFORE the existing slices.

Note `edDef.get(i-1)` indexes the `ElementAnalysis` chain built from the sliceStuff element's **path** — id segments align 1:1 with path segments (id = `name[:slice]` per segment), so the alignment holds; `indexOfName` (L918-928) strips a `:slice` suffix before looking the name up in the parent's child list, returning `-1` when not found (unknown names then sort first).

### 5.4 `analysePath` (L930-939) / `analysePathSegment` (L941-980) — failure modes

`analysePath` splits the sliceStuff element's path and resolves each segment against real definitions, producing the `ElementAnalysis` chain (structure + element + optional forced type; `ElementAnalysis` inner class at L55-84).

- **Root segment** (L942-948): `context.fetchTypeDefinition(pn)`; if null →

  ```java
  String message = context.formatMessage(I18nConstants.UNKNOWN_TYPE__AT_, pn, ed.getId());
  throw new DefinitionException(message);
  ```

  Message text verbatim (Messages.properties:1141): `Unknown_type__at_ = Unknown type {0} at {1}` — formatted with (segment, element id). Thrown at L946.

- **Child segments** (L949-979): resolves via `utils.getChildMap(sed.getStructure(), sed.getElement(), true, sed.getType())` (L951), matching exact name first, then choice stems: a child named `foo[x]` matches segment `fooBar`, recording forced type `bar`/`Bar` (`TypesUtilities.isPrimitive(uncapitalize(tn))` decides casing, L959-971; the stem match is a bare `startsWith` with no validation of the type tail). If nothing matches →

  ```java
  String message = context.formatMessage(I18nConstants.UNKNOWN_PROPERTY, pn, ed.getPath());
  throw new DefinitionException("Unknown path "+pn+" in path "+ed.getPath()+": "+message);          
  ```

  (L974-975). Message text verbatim (Messages.properties:1139): `UNKNOWN_PROPERTY = Unknown property name {0} in path {1}` — so the full thrown text is `Unknown path <segment> in path <path>: Unknown property name <segment> in path <path>`.

These are hard `DefinitionException`s (not log-warns): a sliceStuff element with an unresolvable path that reaches the injection branch aborts snapshot generation.
